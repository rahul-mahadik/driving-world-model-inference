# Research validation protocol — prospective revision 1

**Status: planned, not admitted or executed.** This document defines the next evidence needed for a research benchmark. It is not a completed experiment, a replacement for any registered historical study, or a claim that publication of the software establishes scientific validity. The machine-readable companions in [configs/research](../configs/research/research-plan-v1.json) describe research plans; they are **not executable worker specifications**.

The release provides a reusable, finite-budget configuration-search environment. The current agents select typed settings from fixed domains. They do not edit arbitrary code or write kernels in an adversarial sandbox. Operator correctness and model fidelity use different gates and must remain separate. Existing historical results and incomplete studies remain unchanged.

## Questions and stages

1. **Operator validation:** Does the released 12-task operator suite execute correctly on one declared GPU/runtime, and what do equal-budget random and grid search achieve across repeated episodes after fresh winner confirmation?
2. **Preserved Vista feasibility study:** Can the already registered single off-the-shelf LLM select a configuration and complete fresh, fidelity-gated final evaluation? The frozen V21 plan remains one LLM episode, eight development scenes and four final scenes. No baseline-comparison result follows from it.
3. **Separate Vista comparison:** What do one LLM episode, one random episode and one grid episode achieve with the same four-trial budget on the same fresh physical GPU/runtime? This requires a separately registered study. It is not an extension of the old guard or a completed repeated-policy evaluation.
4. **Repeated comparison and reproduction:** Repeat matched policy episodes, validate the quality gate against human judgments, and reproduce the protocol independently. These require separate admission, costs and storage. They are not promised within the current execution budget.

Stages 1 and 2 are separate cohorts, with different software runtimes and scientific questions. Completing stage 1 does not validate Vista quality; completing stage 2 does not show that LLM search beats simpler methods. A website should expose these distinctions and link to immutable evidence, rather than present a leaderboard before scores exist.

## Operator study: bounded repeated baselines

Freeze the exact bytes of `operator-search-v1`, candidate order, objective, runtime and source before any GPU feedback. The suite contains six training, two validation and four test tasks from GEGLU and GroupNorm+SiLU. Inputs are seeded random tensors. The four test shapes are public and derived from selected historical profiles; they are not secret or globally unseen workloads.

Use the existing [serial policy comparison](../extensions/kernel_tuning/examples/compare_search_policies.py) and CUDA evaluator. Run grid and random search on the two validation tasks and then the four test tasks, with **six episodes per policy per task**, four candidate calls and one fresh eager reference per episode. Use base seed 1901 and the script's exact episode-seed construction. Its alternating policy order gives each task three episodes in each order. The grid prefix and random sampling without replacement remain unchanged. No policy is trained in this study. Validation is a compatibility check; if it motivates a protocol change, freeze a new revision before touching test results.

Keep five warmups and thirty timed samples per measurement, the existing dtype-specific correctness thresholds, and latency-only reward (`memory_weight=0`). Timing excludes preparation, compilation, correctness and warmup, but the wall-time ledger includes them. Report allocated and reserved memory separately; neither is whole-model memory. Run one serial evaluator with an otherwise idle device. Bind input fingerprints, physical GPU, driver and exact runtime to every result.

**Fresh confirmation is required in addition to the existing comparison script.** That script currently reports `selected_config_confirmation_performed: false`. A small reviewed driver must freeze each episode's incumbent and then invoke the existing evaluator for two fresh reference/candidate pairs, once in each order. It must preserve the baseline as the incumbent when no candidate wins, and report that outcome as no improvement. Failed or incorrect candidates consume a trial; failed confirmation is not replaced or converted to a win. The driver is not implemented or GPU-validated by this protocol document.

After all test selections are locked and confirmed, run a separately labeled diagnostic sweep of eager plus all nine candidates on all twelve tasks. Its purpose is suite-wide capability checking and a measured finite-space oracle. Keep these results out of every search policy's observations. Report oracle cost separately, including compilation and failed candidates. A noisy best measurement is an optimistic oracle estimate, not a proven optimum.

| Work | Fresh evaluator calls |
| --- | ---: |
| 72 search episodes: 1 reference + 4 candidates each | 360 |
| 72 frozen selections: 2 new reference/candidate pairs each | 288 |
| Post-selection diagnostic/oracle: 12 × (eager + 9 candidates) | 120 |
| Total, excluding runtime proof and correctness tests | **768** |

The planning envelope is six hours, including a separate pinned runtime build/proof, GPU correctness tests, every measurement stage, inventory, copy, independent verification and cleanup. It is a timeout envelope, not a prediction or guarantee of completion. The existing bounded portable host launcher can run reviewed commands, but a new exact command/source manifest and confirmation driver must be reviewed first. Historical operator runners and guards are not modified or restarted.

Report each task's six episode outcomes, raw selected configuration, pre-confirmation reward, confirmation ratios, correctness failures, total calls and costs. The unit for policy randomness is the episode; the unit for workload generalization is the task. Thirty event samples, six episodes and repeated visits to one tensor are not thirty or six new workloads. With four test tasks and two operator families, use descriptive per-task medians/ranges and disclose every result. Do not attach a population significance or broad kernel-generalization claim to this small study. A fixed one-percent descriptive noise screen may flag tiny gains, but it is not a confidence bound and must not silently change the environment's registered reward.

## Vista feasibility: preserve the registered experiment

The existing [agent study](agent-study-reproduction.md) remains an eight-option FP16 configuration task: decoder chunk size 1, 2, 7 or 14, with the denoiser eager or compiled. It uses unchanged weights, actions, 50 denoising steps, one future, and 24 future frames at 576 × 1024. Reference decoding uses chunk size 14 and eager denoising. No arbitrary code edits, precision expansion, sampler sweep or additional GPU profile pass is admitted.

The existing V21 single-LLM plan uses eight development scenes, four final scenes, seeds 11 and 23, and two repeats. Four search trials each use the same two development scenes and the fixed seed schedule `[11, 23, 23, 11]`, alternating reference-first and candidate-first. Each trial has fresh matched reference outputs; development screening is provisional. Submission locks the development-selected configuration before final generation. Final evaluation uses fresh reference and candidate cells on the four withheld-from-this-agent scenes. The scenes are not certified historically unseen.

The current maximum proxy limits are MAE 0.01, temporal-derivative MAE 0.01 and LPIPS 0.02. They are prospective engineering fidelity limits, **not perceptually calibrated seed-variance thresholds**. Reference same-seed repeats must fit every limit, and the frozen black, frozen-future and reversed-future controls must each breach at least one limit as required by the registered plan. If this fails, stop as inconclusive before search. Cross-seed variability is descriptive and cannot justify increasing a limit. Freeze the timing floor, `max(0.01, maximum paired reference-repeat relative latency difference)`, before candidate feedback. It is an empirical screen, not a statistical confidence bound.

A proxy pass does not prove equivalent realism, trajectory adherence or safety. Complete the actual blinded visual review after exports, retaining every label and disagreement; successful export is not review. Keep the existing small visual-review scope and claim limits. Do not retrospectively qualify the historical H100 compiler timing result using a different GPU or this later quality experiment.

## Separate three-policy Vista comparison

The [prospective comparison specification](../configs/research/vista-three-policy-v1.json) adds one random and one grid episode to a **new** study namespace. It preserves the exact eight-development/four-final membership, seeds, actions, quality limits and four-trial schedule. All three methods get the same candidate domain, trial budget and 13,200-second episode wall ceiling. Count model API calls/time for the LLM and zero such calls for grid/random; equal GPU trial budgets do not imply equal total cost.

Use the existing `SearchBaseline` implementations, with baseline seed 20261114. For this Vista domain, grid's first four configurations are chunk 1 eager, chunk 1 compiled, chunk 2 eager and chunk 2 compiled. This order is a weak, explicit baseline, not an oracle or the strongest autotuner. Random samples without replacement. The LLM's model snapshot, prompt, source, tool schema and API ledger must be pinned prospectively. Do not inspect oracle or final feedback to select any policy's winner.

Lock all three selections before any final-generation feedback. A policy with no eligible selection is reported as failed to select; never substitute a favorable configuration. Final evaluation has sixteen cells per role: four scenes × two seeds × two repeats. The four roles are reference and each policy's selected candidate. For the first two-scene block use reference/LLM/random/grid at repeat 0, reversed at repeat 1. For the second use LLM/grid/reference/random, then its reverse. Each candidate/reference pair sees both orders. This is not a complete four-position Latin-square design.

The same sixteen fresh reference cells are shared by the three final assessments; publish their shared IDs and do not treat the assessments as statistically independent. Each assessment joins the exact sixteen unique corresponding cells. Report every cell and scene-level paired median ratio, all proxy metrics and failures, and each policy's cost from startup through selection and confirmation. Seeds/repeats are nested within four scenes. They do not create sixteen independent scenes or three independent models. One episode per policy supports an execution demonstration and descriptive comparison only; it cannot establish policy superiority.

This complete draft reserves **147,480 seconds of phases within a new 46-hour envelope**, preserving both full evidence copies, separate independent local verification, terminal verification, per-job cleanup, monitoring/provider cleanup and at least the prior plan's unassigned slack. It preserves 191 fresh raw arrays (33,796,939,648 bytes), plus the nine old support arrays and all historical failures. Fresh evidence remains capped at 45 GB with 20 GB free reserve; at least 65 GB must be free after recovering old evidence and before fresh science. If actual files or copy timing do not fit, stop; do not delete old evidence, shorten copy reserves or rerun on a different GPU and pool results. New exact worker bindings and helper review are still required. This option exceeds the currently approved remaining additional execution budget and is **not admitted**.

## What stronger validation would require

A later repeated model study should prospectively target five matched episode groups for each of LLM, random and grid, with fresh per-episode budgets, search histories and final reference/candidate cells. Use episode seeds 1901–1905 and rotate policy order across groups; no episode sees earlier final feedback. All fifteen selections must be locked before any final feedback is made available to policies. Keep the current fixed task and gate when measuring policy variation; an expanded task, additional GPU or relaxed fidelity criterion is a separate study. Report the API's actual determinism limitations rather than asserting that repeated identical requests are independent training runs.

Even reusing one fresh development calibration, this design needs **799 fresh arrays, or 141,380,915,072 raw bytes**, before exports/metadata and the old archive. It does not fit the current 45 GB evidence cap or the current storage admission. A new complete time/cost/storage plan and a durable backup destination are required. The five-episode target is a modest repeated-case study, not a power calculation or a guarantee of a publishable comparative result. Do not launch an underpowered surrogate and label it completion of this plan.

Validate the fidelity gate in a separately registered study before making broad quality claims. Use disjoint development material to choose any new criterion, and freeze it before final evaluation. Include subtle temporal, geometric and action-response degradations as well as the existing catastrophic controls. Have at least two blinded reviewers label the same prospective pairs independently with a fixed rubric; retain disagreements and report the metric/human false-accept and false-reject counts per scene. Report the uncertainty from the number of scenes and reviewers, not the number of video frames. Seed-to-seed variability alone does not establish acceptable perceptual degradation. This human-validation study is currently unbudgeted and cannot change the frozen V21 gates after results.

An independent reproducer should install the released package from a clean environment, fetch licensed assets through the documented route, run the declared protocol without private helper state, and verify fresh evidence and scoring. Report the reproducer's device/runtime separately; agreement across hardware is not permission to pool samples. Failed reproduction, missing assets, unsupported settings and spent compute are results to retain. Wider model/workload coverage and stronger search baselines can then be added as new versions, not as hidden changes to the current task.

## Evidence and reporting contract

- Retain the exact plan, source/runtime/input hashes, all successful and failed attempts, fresh raw arrays, measurement rows, cost ledger, selection locks, scoring receipts, visual labels, copy verification and cleanup receipts. Synthetic results and CPU checks never become GPU measurements.
- Publish measured latency and memory boundaries, cold-start/compile costs and total episode wall time separately. Count reference calls, trials, final confirmation, oracle sweeps, policy training, LLM tokens/API attempts, setup, unsuccessful stages, storage, copy and cleanup. Funding is not usage; reservations are not invoices.
- Freeze analysis before measurements. Publish all planned task/episode outcomes, including unavailable scores. Small-task descriptive statistics must not be relabeled confidence in generalization. Historical cohorts retain their original claim flags.
- Release sanitized evidence and exact commands where licenses permit. Explain omissions. A website mirrors the release, cohort identifiers, statuses and limitations; it is not an alternative source of scores.

The [NeurIPS 2026 Evaluations and Datasets review criteria](https://nips.cc/Conferences/2026/EvaluationsDatasetsReviewerGuidelines) emphasize technical soundness, meaningful evaluation and reproducibility. They do not certify this project. [KernelBench](https://github.com/ScalingIntelligence/KernelBench) is a relevant public kernel-generation benchmark; this release's fixed configuration search is a narrower action space and must not be advertised as equivalent arbitrary kernel generation.
